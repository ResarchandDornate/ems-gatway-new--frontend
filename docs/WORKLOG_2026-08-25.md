# Work log — 25 August 2026

## History on /k: three bugs, one architecture

The reported symptom was that History "feels broken even when it isn't" — slow,
fragile, and vulnerable to any interruption. A screenshot of the 6h view settled
what was actually wrong, and it was more than slowness:

- the x-axis read **07:40 → 09:56** under a **"6h"** label,
- the power line was **flat at 0.0 kW** and SOC read **—**, for a window in
  which the plant was charging at 34.5 kW with SOC moving 100% → 91.7% → 92%,
- throughput read **0.0 kWh**, and the card announced **"Page limit reached"**.

### 1. Every plotted value read zero

The chart drew a flat line along 0 kW, SOC read "—", throughput read 0.0 kWh,
and the row envelope decoded perfectly — `bess_id` matched the filter and
`timestamp_epoch_ms` gave real axis labels. That is why it looked like data
rather than a bug.

**I diagnosed this wrongly at the time, and the correction is on 27 August
below.** The fix that shipped — nullable values end to end, so a gap renders as
a gap — stands on its own and is the one that matters. The cause of the absent
values is still not established.

### 2. The window lied about what it covered

The page budget was `expectedRows = (spanMinutes * 60) / 15 * 2` — a guess that
the historian is 15-second and that both BESS come back in every page. Live data
is one-second and the request is filtered to one source, so the guess was 15x
short. A six-hour window budgeted two pages, bought 10,000 rows, drew 2 h 16 m of
them, and reported "page limit reached": a client-side budget presented as a
limit of the plant.

Coverage is now measured and reported as a fact — "Covers 21 h of 24 h", with
the uncovered stretches named — and never inferred from a row count.

### 3. 8.7 MB an hour, to draw four numbers

The gateway offers no downsampling; §8 exposes `from`, `to`, `limit`, `order`
and `format` and nothing else. A pre-aggregated endpoint remains the right
long-term answer and is gateway-team work. What did not need them is removing
the phone from the problem.

`gateway/series.ts` reads the gateway server-side and returns buckets. It keeps
epoch-aligned 30-minute chunks under the caller's entitlement scope; history is
immutable, so a chunk that has ended is correct forever and is never read twice,
while the trailing chunk is extended from its own high-water mark. Each request
does a bounded slice of gateway work and returns whatever coverage exists, so a
wide window fills progressively rather than hanging, and a failure costs one
chunk instead of the window. There is no longer a long request to interrupt.

Measured against a one-second stub:

| | before | after |
|---|---|---|
| 1 h to the phone | 8.7 MB / 33 s | 24 KB |
| 24 h | not attainable | 86,670 rows as 37 KB |
| repeat view | full refetch | 9 ms |
| window slid 2 min | full refetch | 74 ms, 24 new rows |

Totals stay exact: energy, peaks and the SOC range accumulate over every raw row
before any bucketing. The plotted line is a mean and is labelled as one —
"5 s mean", "2 min mean" — because a sub-bucket spike lives in Peak power rather
than on the line, and saying "1s resolution" over a mean would misdescribe what
sits between two points.

### The safety net

The reason bug 1 survived is that a decode failure and a quiet plant rendered
identically. Both are now impossible to confuse:

- `CurvePoint.power` is nullable end to end and `connectNulls={false}`. A
  missing measurement is a gap in the line. No caller writes `?? 0`.
- Rows the build cannot decode are counted and the screen names the columns it
  actually received: "3,565 rows came back in a shape this build could not
  decode … Columns seen: measurements{p_kw_total,state_of_charge}". If the
  gateway changes shape again, that is a one-glance diagnosis instead of an
  inference from a flat line.

## Value: an eased number that never arrived

Surfaced by the above, and older than it. `useEased` only advanced its starting
point when a run reached `t === 1`, so a target that changed mid-ease stranded
the display, and a later `a === b` short-circuit stranded it permanently. Worse,
convergence was delegated entirely to `requestAnimationFrame`, which stops while
a page is backgrounded — and, as this app's own preview demonstrated, a document
reporting `visibilityState: "visible"` is still no guarantee that frames are
produced. Where frames stopped, the number simply stopped: a card read
**40.95 kWh** beside a chip reading **833.7 kWh** for the same quantity.

The start point is now what is actually on screen, written every frame, and a
620 ms timer — not the frame loop — owns the promise in the function's docblock.
The easing is decoration; landing on the real number is not. Fixed identically in
`mobile-app/` and `mobile_app_kunal_backend/`, which carry the same component.

## Not fixed here

- **The gateway still has no downsampled endpoint.** Everything above moves the
  cost off the phone and pays it once; it does not make the board faster. A
  cold 24-hour window is still bounded by how quickly the gateway can read
  86,400 rows out of SQLite. Server-side downsampling or a pre-aggregated
  endpoint remains the genuine fix, and remains gateway-team work.
- **The chunk cache is in-process.** A redeploy starts cold and refills. Making
  it durable is a real improvement and an infrastructure dependency; not worth
  taking on until someone asks.
- **The live row shape is inferred, not observed.** `rows.ts` reads the
  flattened `colKey` spelling this repo documents, and reports anything it
  cannot read rather than guessing. One real history response body would
  confirm it outright.

# Correction — 27 August 2026

The handover package of 10 August (API Reference, endpoint inventory, 63-signal
profile, and a real 24-hour export) was supplied and checked against the code.

## What I got wrong

I claimed `/api/fast-bess/history` returns rows with flattened columns —
`"PCS total_active_power"` — and that reading the `pcs_values` / `bms_values`
envelope was why every history value came back undefined. That was inferred
from `colKey` in `signals.ts`, and it is wrong.

The API Reference is explicit: *"fast_bess pcs_values/bms_values | object map |
Compact value-only signal maps for 1-second historian"*, with `schema_version`
2 and `write_mode` `value_only`. The envelope this build originally read is the
documented one. The flattened spelling is the **CSV export** format — the
24-hour export in the package uses it for all 72 of its columns.

So the cause of the flat zero line is **not** established. What is established,
and was worth fixing regardless: a `?? 0` at the chart made "no value" and
"measured zero" render identically, and nothing on screen could tell them
apart. Values are nullable end to end now.

`gateway/rows.ts` keeps the envelope as its first and normally only lookup. Its
other candidates are defensive and cost nothing; they are no longer described
as necessary.

## What the package confirmed

| Checked | Result |
|---|---|
| History query parameters | `order=asc`, `limit=5000`, `format=compact`, inclusive `from_epoch_ms`/`to_epoch_ms`, next cursor at last `timestamp_epoch_ms` + 1 — all match §8.1 |
| Page cap | 5000, matches; spec default `limit` is 100 and default `order` is `desc`, both of which we override correctly |
| 63-signal profile | All 63 match `signals.ts` on asset, name, label, category and unit. Zero mismatches |
| Login response | `expires_in_sec`, read correctly, with the documented 28800 default |
| `/api/telemetry` | Accepts `source_id`; our call is correct |
| Quality values | `good, partial, stale, bad, missing` — matches `types.ts` |
| Role model | `customer_admin` for read-only, `internal_admin` for control — matches |

The export also corroborates two findings this build already surfaces:
`charge_discharge_power` is 0.00 across all 141,288 rows, while
`total_active_power` moves between -44.70 and +24.50 kW.

## What the package changes about the plan

Nothing structural. §2 of the feature specification asks for exactly the
architecture `gateway/series.ts` implements — "a bounded ingestion worker that
authenticates, pulls metadata, and incrementally imports Fast BESS history
using time-cursor pagination" — and names the Flutter/mobile client's job as
"show live monitoring and filtered historian views", explicitly *not* "act as
the permanent server-side historian". The chunk cache is that worker, minus
durability.
