## 1. The most serious bug: the app was unusable on every fresh install

**`4f1deaf` — `fix(android): hide the splash on a fresh install`**

The packaged app sat on its splash screen forever. The login form was rendered
and laid out underneath it the whole time, unreachable.

**Cause.** `Gate` in `MobileShell.tsx` returns early when there is no session,
and an early return drops `children`. `children` contained `<NativeChrome />`,
which is the only caller of `hideSplashAfterPaint()`. `capacitor.config.ts` sets
`launchAutoHide: false` precisely so that call is the only thing that hides the
splash. On any build with no stored session — every fresh install — nothing did.

**Proof, from `adb shell dumpsys activity top`:**

```
before: mLastPerformTraversalsFailedReason=predraw_...SplashScreen$2   (stuck)
after:  mLastPerformTraversalsFailedReason=view_not_visible            (released)
```

**Fix.** `NativeChrome` moves from `children` to a new `chrome` prop, rendered
inside `ThemeProvider` (so it still reads the theme) but outside the gate. A
`ReactNode`, so the shared file stays ignorant of Capacitor.

**Why it survived this long.** It cannot be reproduced in either shell anyone
tests in: the web build has no splash, and `:5180` has no native layer. Only an
installed APK with no session shows it — the one configuration nobody could open
until an emulator existed. This single find justifies the emulator setup below.

> The same bug would have stranded the iOS build. It did not, because it was
> already fixed by the time iOS was added.

## 2. `/k` in a browser — decided and implemented

**`b5e7071`, `416c2a3`, `af16e75`**

`/k` is gated to the packaged app: the proxy requires an app token and only the
APK carries one. **Decision taken: the token is never served to the page.**
Serving it would hand it to everyone who loads `/k` and make the gate decorative.

Three things were wrong with how that decision surfaced:

| Problem | Fix |
|---|---|
| The proxy returned a bare `{ error: "forbidden" }`, indistinguishable from the gateway's own role-403. The login screen rendered it as **"that account is not permitted to sign in here"** — blaming an account that was never consulted, since the refusal happens before the gateway is contacted | `app_token_required` with a `detail` saying it is not the user's account |
| A browser was offered a sign-in form that could never succeed | `AppOnlyScreen` — the form is not shown at all. A door that cannot open should not have a handle |
| The new screen printed the backend host, copied from `LoginScreen`. There it earns its place (a packaged APK has its server baked in). Here it can only ever render the constant `"same origin"` — jargon on the one page whose job is to be understood by a non-developer | Removed |

`app/k/layout.tsx` reads `GW_APP_TOKEN` at request time and is `force-dynamic`.
The image is built **without** that variable — it comes from `~/portals/.env` at
container start — so a prerender would bake in "ungated" forever.

**Verified in production:** `/k` shows the notice; the RSC payload carries
`gated: true`, confirming the server variable is set.

## 6. History charts were truncating 60% of every window

**`fcf25d1`** (second half)

Three lines disagreed:

- `data.ts` asked for `limit: 5000`
- `client.ts` silently clamped it to `PAGE_LIMIT = 2000`
- `data.ts` budgeted its page count assuming **5000 rows per page**

So the budget was 2.5× too optimistic and the window was cut off long before
`maxPages` was reached.

| Window | Rows needed | Pages budgeted | Rows delivered (before) |
|---|---|---|---|
| 24 h | 11,520 | 3 | 6,000 — **~52%** |
| 7 d | 80,640 | 16 | 32,000 — **~40%** |

`PAGE_LIMIT` was 2000 with no stated reason, while two comments already said the
gateway's cap is 5000 (§8 of the API Reference). Raised to 5000.

**Measured on device: a 24-hour window went from 6,000 samples to 15,000, in the
same three requests.**

### This fixed completeness, not speed

24 h still takes ~75 s. Paging is inherently sequential — each page starts at the
previous page's last timestamp — and this gateway answers a history call in
16–25 s. The fix changed how much each page returns, not how many round trips
there are.

**To make it actually faster:** `from`/`to` are explicit parameters, so the range
can be split into **concurrent sub-windows** instead of cursor-chained (~75 s →
~25 s for 24 h). Cap concurrency at 2–3: §8 and the retry logic both say this
board degrades under load. Left as a separate change so it can be judged on its
own.

## 8. iOS

**`46a785b`** — §10.5 was blocked on Xcode not being installed. It now is, so
the platform is in: `cap add ios`, built for `iphonesimulator`, installed and
launched on an iPhone 17 Pro. The login screen renders against

- **Capacitor 8 uses Swift Package Manager, not CocoaPods.** No Podfile, no

- **The proxy already allowed it** — `capacitor://localhost` was put in

- **Cost:** simulator builds need no signing and no membership. **$99/year**

- First build takes ~25 min (Capacitor compiles from source via SPM).
- Icon and splash are Capacitor defaults — the same placeholder situation as

> Apple's minimum-functionality rule is stricter than Google's. A read-only
> dashboard is the category most likely to be rejected — which is why the
> handoff flags push notifications as "what gets past it". Worth weighing before
> spending the $99.

## 10. A deploy that died, and what it broke

The deploy for `4f1deaf` was **cancelled at 15m26s** — the 15-minute job timeout
§2 warns about. Between roughly 12:28 and 12:44 the origin was flapping and
Cloudflare served its own 502 pages. **A Cloudflare error page carries no
`Access-Control-Allow-Origin`**, so the app reported them as CORS failures, cached
them, and the battery-unit picker showed "the gateway has not reported a unit
yet".

Nothing was wrong with CORS. Direct `curl` proved the config correct: preflight
204 with `access-control-allow-origin: https://localhost`, and the GET returning
401 *with* the header. After a re-run (8m30s, green) and an app relaunch: zero
CORS errors, live data, **both EMS listed — BESS 1 and BESS 2, both Reporting**.

**Lesson worth keeping:** a Cloudflare 5xx during a deploy is indistinguishable
from a CORS misconfiguration at the call site. Check deploy status before
debugging CORS.

## 13. Grid frequency was hidden by a nullish fallback

**`aafb88f`** — the card read **0.00 Hz on a live grid** while the PCS reported
50.19 the whole time. The mapping was correct; the fallback was not.

`site.gridHz ?? r.gridHz`, and `??` only falls through on null or undefined. The
utility meter returns `0.0` at `quality: "good"` — §8 records it reading a flat
zero and notes it is unconfirmed whether that meter is wired — so `leafValue()`
yields `0`, not null, and `0 ?? 50.19` is `0`.

Zero now counts as absent **for frequency only**. A connected grid never
measures exactly 0.00 Hz. It does not generalise: 0 kW and a 0.00 power factor
are real readings on an idle plant. Verified on device: **50.10 Hz**.

The power factor on that same card is correct at 0.00 — `total_active_power` is
0.0, and the PCS's own phase power factors are unusable anyway
(`phase_a_power_factor` reads 65.53, outside the −1…1 a power factor occupies).

**All 40 mappings were then audited** against the telemetry data dictionary:
12 site signals and 28 fast-historian signals, each checked three ways — in the
dictionary, in the declared 63-signal profile, and present in a live capture.
No other broken name, and no other nullish fallback a zero can defeat.

## 15. A dispatch control panel

**`c31c8e0`** — charge, discharge and standby on a new Control screen reached
from System. Three independent gates, in three places:

1. **The gateway grants `internal_admin`**, per request. A customer token gets
   403 from the gateway whatever the client does.
2. **`GW_ALLOW_WRITES` is set**, or the proxy refuses before the gateway is
   contacted.
3. **The path is on the proxy's dispatch allowlist.**

That third gate is new and it *narrows* the flag. `GW_ALLOW_WRITES` previously
opened every non-GET on every path — so enabling a control panel would also
have opened `storage/cleanup`, `storage/vacuum`, `logs/test` and
`server-upload/upload-once`. The thirteen dispatch paths are now enumerated from
the API Inventory, anchored `^...$` so a prefix match cannot admit whatever the
gateway adds under `control/` later.

The interaction is **staged, never immediate**: moving a control sends nothing,
a confirmation sheet restates the command with the actual numbers and the
current SOC, and only an explicit press dispatches. Dispatch is blocked outright
while telemetry is stale — a system whose present state is unknown is never
commanded.

For an account without the role the controls are **absent, not disabled**.
Verified on device with `customer`: "Dispatch is not available to this account".
